# 店舗管理SaaS（仮称）実装準備ドキュメント

参考資料：原価計算帳（トマトラーメンあうわ・社内ツール／デザインとUXの参考）
ベース仕様：スナック・ラウンジ向け店舗管理SaaS マスタープロンプト一式（4文書）

---

## 0. 結論（技術方針の提案）

原価計算帳と同じ「HTML1枚＋Supabase鍵を直書き」の構成は、**社内の1店舗用ツールとしては正解**ですが、以下2点が理由で、他店舗に課金販売するSaaSにはそのまま使えません。

1. **Stripeの秘密鍵・Webhook検証はサーバー側でしか扱えない**（ブラウザに置いた瞬間、誰でも不正決済・不正Webhookが可能になる）
2. **店舗間データ分離**を「フロントのstoreIdフィルタ」だけに頼ると、URLやリクエストを書き換えれば他店舗のデータが見えてしまう。DB側（Row Level Security）で強制する必要がある

そのため、**UI/UXのテイスト（帳簿風デザイン、カードUI、モーダルでの確認、原価計算帳で採用した「読み込み失敗時にデータを消さず再試行させる」設計思想）は踏襲**しつつ、裏側の構成を以下のように変えます。

## 1. 技術スタック（提案）

| 領域 | 採用技術 | 理由 |
|---|---|---|
| DB / 認証 | Supabase (Postgres + Auth + Row Level Security) | 店舗分離をDB側で強制できる。社内アプリと同じ技術で学習コストが低い |
| 秘密鍵を要する処理 | Netlify Functions（サーバーレス） | Stripe秘密鍵・Webhook署名検証をサーバー側に隔離 |
| 決済 | Stripe Checkout / Billing / Customer Portal / Webhook | マスタープロンプト仕様どおり |
| フロント | 素のHTML/JS（原価計算帳と同系統）、ページは複数分割 | フレームワーク学習コストを増やさない。ただし1ファイルに全部詰め込む方式は今回は不可（LP・アプリ・管理画面・デモが別物のため） |
| デプロイ | Netlify（新規サイトとして分離。自店舗版とは別URL・別プロジェクト） | 自店舗版に影響を与えないため |

---

## 2. 自社データの扱い（最重要方針）

- 実店舗名「あうわ」「スナック手紬」「トマトラーメン あうわ」等は一切含めない
- スタッフ実名・実際の時給・実際の給与額・実売上等は一切使わない
- 開発・デモ用のサンプルデータのみ使用する
  - サンプル店舗名：`DEMO LOUNGE`
  - サンプルスタッフ：`スタッフA` `スタッフB` `スタッフC`
  - サンプル数値：日報の来店8組15名、現金85,000円／カード70,000円／電子決済15,000円など、マスタープロンプト記載の例をそのまま採用
- 自店舗版（現行の給与・バック管理アプリ）のDB・URL・ログイン情報には一切触れない。新規のSupabaseプロジェクト／Netlifyサイトとして完全分離する

## 4. 開発の進め方について（提案）

このプロジェクトは「認証・複数店舗のDB設計・Stripeのサーバーレス関数・LP・デモ環境・SUPER_ADMIN・マニュアル機能」と、ファイル数・サービス数が非常に多い**複数ファイル／複数サービス構成のプロジェクト**です。

このチャット画面でも設計書やSQL、個別ファイルの雛形は作成できますが、

- Gitでのバージョン管理
- Netlify Functionsのローカルテスト
- 継続的なファイル間の整合性確認

を伴う本格的な実装フェーズは、**Claude Code（デスクトップアプリ）でリポジトリごと作業する方が、途中経過を壊さず・やり取り回数も少なく進められます**。本日はこの場で「土台（DBスキーマ／フォルダ雛形／最初のLP・デモ用データ）」まで用意し、以降の本実装はClaude Codeへの引き継ぎを推奨します。

## 5. Stripe実装方針（要点）

- Checkout（プラン選択→決済）／Billing（サブスク管理）／Customer Portal（カード変更・解約）／Webhookの4本柱
- **契約の有効化はWebhookでの状態確認後のみ**（success_url到達だけでは有効化しない）
- Webhookは署名検証必須、イベントIDで冪等性を担保（同じイベントの二重処理防止）
- 支払い失敗時は即削除せず `subscription_status = past_due` に変更し、必要に応じて機能制限のみ

|---|---|
